### Primary keys, foreign keys and relationships

- **Primary key:** uniquely identifies each row. Each table uses an identity column that PostgreSQL generates automatically, so IDs are never typed by hand and can never repeat.
- **Foreign key:** a column in a child table that must match an existing primary key in a parent table. `sales.customer_id` references `customers`, and `sales.medicine_id` references `medicines`. PostgreSQL rejects a sale for a customer or medicine that does not exist, and (with `ON DELETE RESTRICT`) refuses to delete a customer or medicine that already has sales.
- **customers → sales is one-to-many:** one customer can make many sales; each sale belongs to exactly one customer.
- **medicines → sales is one-to-many:** one medicine can appear in many sales; each sale row refers to one medicine.
- Together, `sales` resolves the many-to-many relationship between customers and medicines. Customer and medicine details are stored once, so there is no duplicated data to get out of sync.

## Section 3: Database and Table Creation

```sql
CREATE DATABASE twin_202512587_pharmacy_system;

CREATE TABLE customers (
    customer_id     INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name      VARCHAR(50)  NOT NULL,
    last_name       VARCHAR(50)  NOT NULL,
    phone           VARCHAR(15)  NOT NULL UNIQUE,
    email           VARCHAR(100) UNIQUE,
    address         VARCHAR(150),
    registered_date DATE         NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE medicines (
    medicine_id    INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    medicine_name  VARCHAR(100)  NOT NULL,
    category       VARCHAR(50)   NOT NULL,
    unit_price     NUMERIC(10,2) NOT NULL CHECK (unit_price > 0),
    stock_quantity INT           NOT NULL DEFAULT 0 CHECK (stock_quantity >= 0),
    expiry_date    DATE          NOT NULL,
    status         VARCHAR(20)   NOT NULL DEFAULT 'Available'
                   CHECK (status IN ('Available','Low Stock','Discounted','Expired'))
);

CREATE TABLE sales (
    sale_id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id    INT           NOT NULL,
    medicine_id    INT           NOT NULL,
    quantity       INT           NOT NULL CHECK (quantity > 0),
    total_amount   NUMERIC(10,2) NOT NULL CHECK (total_amount >= 0),
    sale_date      DATE          NOT NULL DEFAULT CURRENT_DATE,
    payment_method VARCHAR(20)   NOT NULL
                   CHECK (payment_method IN ('Cash','Mobile Money','Card')),
    CONSTRAINT fk_sales_customer FOREIGN KEY (customer_id)
        REFERENCES customers (customer_id) ON DELETE RESTRICT,
    CONSTRAINT fk_sales_medicine FOREIGN KEY (medicine_id)
        REFERENCES medicines (medicine_id) ON DELETE RESTRICT
);
```

**Q5.3 Related record** — a sale for the new customer.

```sql
INSERT INTO sales (customer_id, medicine_id, quantity, total_amount, sale_date, payment_method)
VALUES (
  (SELECT customer_id FROM customers WHERE phone_number = '0788445566'),
  (SELECT medicine_id FROM medicines WHERE medicine_name = 'Omeprazole 20mg'),
  2, 1400.00, '2026-10-25', 'Cash');

SELECT s.sale_id, c.first_name || ' ' || c.last_name AS customer_name, m.medicine_name,
       s.quantity, s.total_amount, s.sale_date
FROM sales s
JOIN customers c ON s.customer_id = c.customer_id
JOIN medicines m ON s.medicine_id = m.medicine_id
WHERE s.sale_id = (SELECT MAX(sale_id) FROM sales);
```

| sale_id | customer_name | medicine_name | quantity | total_amount | sale_date |
|---|---|---|---|---|---|
| 17 | Sandra Uwimana | Omeprazole 20mg | 2 | 1400.00 | 2026-10-25 |

*Explanation:* the foreign keys were filled with real parent IDs (customer 7 and medicine 9), and the join proves they resolve. The `sale_id` is 17 because PostgreSQL does not reuse identity numbers after rows are deleted (duplicate rows from an accidental double insert were removed earlier). Trying a non-existent customer (e.g. 999) is rejected with `violates foreign key constraint "fk_sales_customer"`.

## Section 6: Conclusion

In this project I learned how to design a relational database by splitting a pharmacy into three related tables and creating the parent tables before the child table. Primary keys generated with `GENERATED ALWAYS AS IDENTITY` identify each row uniquely, while foreign keys in `sales` keep every sale linked to a real customer and medicine. I practised inserting and retrieving data with `SELECT`, `WHERE` and `ORDER BY`, and combining related records with `INNER JOIN`, `LEFT JOIN` and multi-table joins, and I saw that LEFT JOIN keeps unsold medicines that INNER JOIN would hide. I learned to update records safely by checking the target rows first, using a precise `WHERE` clause, and verifying afterwards. Finally, I learned that `ALTER TABLE` changes the structure rather than the data, and that renaming a column, widening a data type and adding a column must be done without breaking keys or existing records.
